# One generic "wrong password" rejection for bad password and gone entries

Verifying a salted scrypt password cannot happen inside the `WHERE` clause of a single `UPDATE`/`DELETE` — the stored salt and hash must first be read back (`SELECT password_hash FROM entries WHERE id = $1`) and compared in server code, since scrypt is a one-way KDF the database cannot evaluate inline. Edit and delete therefore run as: fetch the row by id, verify the supplied password against its stored hash in application code, then act — `UPDATE`/`DELETE ... WHERE id = $1` — only on a match, rechecking the affected-row-count in case the row vanished between the read and the write (e.g. a concurrent delete from another tab).

Whether the failure is "no such id," "password didn't match," or "id existed at read time but was deleted before the write," the visitor sees the same on-screen rejection, explicitly stating that the password was wrong (the brief requires a stated reason, and "wrong password" is that reason). We deliberately do not add a separate "this entry no longer exists" message: doing so would let a caller distinguish a bad guess from a real id, turning the id into an oracle for which ids currently exist. This is a one-way door once real users start depending on the error text, so it's recorded rather than left implicit.
